# Red Point Church OS — Version 8.0

Version 8 is the transition from an AI-enabled application to an AI-operable institution.

## Core contract

`Agent → Permission → Context → Tool → Action → Verification → Outcome → Audit → Learning`

The system no longer treats an agent as a prompt with broad application access. An agent must be registered, enabled, explicitly permitted to use a specific tool, and constrained by an execution mode and approval policy.

## Operating architecture

Mission → Organisational State → Workflow → Dispatch → Agent Runtime → Tool → Action → Verification → Human Exception → Outcome → Institutional Learning

## What remains human

Pastoral judgment, theological authority, spiritual discernment, relationships, discipleship, culture, leadership and consequential exceptions remain human responsibilities.

## What the system can increasingly own

Remembering, checking, routing, monitoring, deterministic operational execution, evidence collection, exception detection, follow-up and repetitive low-risk work.

## v8 safety invariants

1. No arbitrary mutation tool.
2. No execution without an explicit agent/tool permission.
3. High-risk and human-only actions cannot be silently executed.
4. Idempotency is mandatory for queued agent actions.
5. Claimed work is concurrency-safe.
6. Every completed action produces verification and outcome evidence.
7. Every important runtime action produces an audit event.
8. AI recommendations are not silently converted into human decisions.

## Background execution

The runtime is execution-ready, but hosted scheduling is deliberately not faked. Supabase supports scheduled Edge Function invocation with `pg_cron` and `pg_net`; those extensions are not currently enabled in this project. The next infrastructure step is therefore an explicit scheduler enablement and worker deployment, not pretending a background worker already exists.
